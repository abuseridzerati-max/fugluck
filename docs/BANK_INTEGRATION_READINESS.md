## Current provider abstraction and where answers land

The interface is [`PaymentProvider`](../packages/server/src/payments/provider.ts). It uses `ProviderRecord {reference, operation, amountMinor, currency, status, idempotencyKey}` and `ProviderEvent` with `eventId`/`occurredAt`. Statuses are only `PENDING | SUCCEEDED | FAILED`; operations are `DEPOSIT | PAYOUT | REFUND`. `ProviderError` distinguishes `TIMEOUT`, `UNAVAILABLE`, `REJECTED`, `INVALID_SIGNATURE`, `NOT_FOUND`. [`FinancialFlows`](../packages/server/src/payments/financialFlows.ts) owns operation/ledger transitions. The local [`MockPaymentProvider`](../packages/server/src/payments/mockProvider.ts) stores records in memory. The [`HostedMockPaymentProvider`](../packages/server/src/payments/hostedMockProvider.ts) is staging-only, deterministic, database-observing and has no external calls.

| Bank question / operation | BUILT source behavior and precise landing point | PLANNED bank-dependent work / gap |
| --- | --- | --- |
| Create deposit/payment; supported methods, payer details, URLs | `FinancialFlows.requestDeposit` validates the requested amount/currency and writes `deposit:<client idempotency key>` as `REQUESTED`; `submitDeposit` calls `PaymentProvider.createDeposit` with the persisted amount/currency and operation ID, then stores `provider_reference` and `EXTERNAL_PENDING`. An immediate `SUCCEEDED` create response does not credit funds; a verified event is still required. | Adapter translates request/response and any hosted-page/redirect token. Current `ProviderRecord` has no redirect or payer fields; do not expand it until bank and product flow are known. |
| Payment status/lifecycle | `PaymentProvider.getDeposit(reference)` exists in both mocks. | No `FinancialFlows` status-polling or terminality translator is wired. Define mapping for bank intermediate/final/reversal states and an operator-safe polling job only after bank semantics arrive. |
| Callback/webhook, signature and replay | `verifyWebhook(rawBody, signature)` runs before `handleWebhook`; handler hashes raw body, rejects reused event ID with different payload, matches stored reference/amount/currency/kind, records `APPLIED`, `OUT_OF_ORDER`, `MISMATCH` or `UNMATCHED`. Mock uses HMAC-SHA256 and constant-time comparison. Hosted `/provider-event` is a staging-only operator harness. | Adapter verifies bank-specific signature/authentication, timestamp/key rotation and authentic payload schema. A real inbound route, rate/size/replay controls and callback routing are **not built**; hosted mock route must never become the bank endpoint. A callback before the provider reference is stored is recorded as unmatched, so bank delivery/order and recovery semantics must be designed. |
| Deposit confirmation/failure | Verified `DEPOSIT_SUCCEEDED` posts `PROVIDER_CLEARING` → `USER_AVAILABLE` once and marks `CONFIRMED`; verified failure marks `FAILED` without credit. Browser redirect never credits. | Resolve bank finality, late reversal/chargeback and settlement fees; current terminal `CONFIRMED` rejects later events as out of order. |
| Refund/reversal/dispute | `PaymentProvider.refund` is declared; in-memory mock can create a refund record. `HostedMockPaymentProvider.refund` throws `UNAVAILABLE`. `CommercialAccountingAdapter.refundCompetition` compensates **competition entry** in the ledger, not an external deposit refund. | No real provider refund/chargeback operation lifecycle or ledger treatment exists. The current reconciliation loop would flag an in-memory mock refund record without an operation as `PROVIDER_WITHOUT_OPERATION`. Bank refund API, partial amounts, reversals/disputes and linked reference semantics need a separately reviewed design after answers, not a mock substitution. |
| Create withdrawal/payout and beneficiary | `requestWithdrawal` checks eligibility and balance; `reserveWithdrawal` moves `USER_AVAILABLE` → `USER_WITHDRAWAL_RESERVED`; `submitWithdrawal` sets `SUBMITTING` before `PaymentProvider.createPayout` and records `PROCESSING` plus provider reference on response. An immediate `SUCCEEDED` create response does not complete the payout; a verified event is still required. | Adapter maps bank beneficiary/verification/API details. Current request/provider contract has no destination data; payout destination custody and approval flow are **not built**. |
| Payout status, completion/failure | `PaymentProvider.getPayout(reference)` exists in mocks. Verified payout success moves reserved funds → `PROVIDER_CLEARING` and marks `COMPLETED`; verified failure reverses to available and marks `REVERSED`. Definitive create rejection also reverses; pre-submission cancellation is permitted. | Status polling and bank state/finality mapping are not wired. Clarify bank returns/recalls after apparent success and operator handling. |
| Provider IDs, correlation and idempotency | `commercial_operations.provider_reference` binds one provider reference; event ID and payload hash are stored in `commercial_provider_events`. Operation ID is reused as provider idempotency key. Local mock rejects same key with changed amount/currency. | Map bank payment/payout/refund/settlement IDs and idempotency retention/scope. If a bank lacks strong idempotency, design lookup/hold/manual resolution before any payout retry. Multiple provider references per operation are not modeled. |
| Timeout/retry | Deposit creation can leave `REQUESTED`; a later `submitDeposit` retries the same key. Payout timeout/unavailability becomes `SUBMISSION_UNCERTAIN`, funds remain reserved, and same-key retry is permitted; cancellation after submission is denied. | Define exact timeout, retry/backoff/rate-limit and lookup-before-retry rules from the bank. Do not infer failure from a network timeout. Existing hosted retry route is mock-only. |
| Reconciliation/reporting | `PaymentProvider.listRecords()` feeds `FinancialFlows.reconcile`: orphan records, amount/currency mismatch, provider success without ledger, ledger terminal without applied event, anomaly events, stuck pending after one hour, duplicate prizes and unbalanced ledger. Hosted mock synthesizes records from the operation/event tables. | Real provider listing/settlement-file import, pagination, completeness, fees, partial refunds, dispute and bank-balance parity are **not built**. One-hour threshold is an engineering placeholder, not an SLA. |
| Authentication, limits, KYC/AML and operations | [`eligibility.ts`](../packages/server/src/payments/eligibility.ts) defaults all financial actions OFF and requires explicit jurisdiction/limit policy; risk case restriction is checked by `FinancialFlows`. [`commercialSafety.ts`](../packages/server/src/config/commercialSafety.ts) refuses real-money flags and reserved provider secrets in this release. | Bank credentials, KYC/AML facts, legal thresholds, compliance ownership, finance-admin controls, production secret stores and go-live certification remain external decisions. No flag may bypass current refusal. |

**Implementation mapping for intake answers:** identity/docs/environments/auth/certificates/mTLS/IP allowlists → a future provider adapter and separate server-side secret/network configuration; payment methods/GEL/amounts/payer/status/error/rate limits → adapter plus `FinancialFlows`/eligibility policy; callback schema/signature/ID/retry → adapter `verifyWebhook`, a separate inbound route and `commercial_provider_events` review; beneficiary/payout lifecycle → adapter `createPayout`/`getPayout` plus a separately reviewed destination and payout policy; refunds/reversals/chargebacks → reviewed flow, accounting and audit model before code; idempotency/timeout semantics → `submitDeposit`/`submitWithdrawal` retry design; reconciliation/files/settlement/fees → `listRecords`, `reconcile`, `CommercialLedger` and operator reports; bank KYC/AML/onboarding/SLA/support → policy, operating procedures and launch gate. Do not assume the existing narrow interface fits all bank features without changes.

**Finding reverified read-only today:** `https://arcadeclash-client.vercel.app` returned HTTP 200 and asset `/assets/index-BMOhywaz.js` with SHA-256 `394007635f52addd95f3f886bb17594069486d12400f73a6e81ec9d741fb5e59`; its compiled code still contains `https://api-staging.fugluck.com`. Source `packages/client/src/lib/api.ts` routes browser API calls through `VITE_API_URL`; `packages/client/deploymentConfig.ts` intentionally rejects a Production build, and server `config/deploymentIdentity.ts` rejects Production startup. The older shared Vercel Production/Preview `VITE_API_URL` caused the live bundle issue; the new branch-scoped Preview override does not fix an already deployed Production asset. No currently accepted separate Production API/DB was identified in prior provider inventory; that inventory has limited scope.

1. **Decide the Production frontend action with explicit Production authorization.** If no independent Production stack is ready, retire/disable the existing public Production frontend to stop routing users toward staging. Otherwise establish the independent stack below and replace its build. A staging branch push, Preview alias or staging API CORS relaxation is not remediation.
2. **Inventory and register independent resources.** Identify Production frontend project/alias, API service, database/project/region, identity provider, provider merchant account, secret store, DNS, support ownership and recovery account. Require distinct resource IDs and credentials from staging. No Production database may be the Frankfurt staging project `gzfcucvxfzzjzjtgkwpd` or use its registered routing fingerprint.
3. **Review source/config changes on an isolated branch.** Extend `getClientDeployment` to accept only an explicitly registered Production API origin and `VITE_APP_ENV=production`; remove the staging fallback for any Production host and reject a shared Production/Preview `VITE_API_URL`. Extend `validateDeploymentIdentity` for a separately reviewed Production service ID, project/ref, routing fingerprint, region, origins and host-only cookie policy. Keep fail-closed behavior for unknown targets and every money action disabled. These are **PLANNED code changes**, not changes made in this pack.
4. **Provision under separate approval.** Create independent API/DB/secrets and Production-only Vercel variables; ensure no `STAGING_MOCK_*`, staging synthetic IDs, mock key, bank sandbox secret or staging DB URI is inherited. Keep real-money flags absent/false and real-provider secrets absent until a separate accepted integration. Do not put server credentials in `VITE_*` variables.
5. **Isolate browser/auth boundaries.** Production `CLIENT_ORIGIN`, `APP_URL`, `ALLOWED_ORIGINS` and Socket.IO origins must contain Production frontend only; staging retains its sole staging origin. Remove the shared `VITE_API_URL` and unused shared `VITE_SUPABASE_*` values during the controlled Production action. Use host-only Secure/HttpOnly/SameSite cookies (no `.fugluck.com` domain), distinct JWT secret and environment-bound issuer/audience. Verify browsers cannot carry staging sessions into Production and vice versa.
6. **Migrate and validate independently.** Make a protected Production backup/restore plan, run the reviewed migration chain against the identified Production database only, then compare every journal hash/head using `enforceMigrationIdentity` before traffic. Never copy staging financial rows, synthetic accounts or credentials. Record a distinct Production database fingerprint, least-privilege runtime role and approved migration operator.
7. **Gate the actual Production change separately.** Obtain explicit Production deployment/configuration authorization, then deploy matched frontend/API revisions with money OFF. Verify `/deployment.json`, `/health`, `/api/health`, Production database identity/migration head, asset API origin, TLS, CORS/cookies, negative staging cross-origin checks, catalog cold/warm behavior and rollback. Re-check staging revision/data unaffected. Production deployment is outside this task.
8. **Operations before acceptance.** Define monitoring/page owners for API/DB/migrations, callback failure, payout uncertainty, reconciliation, authority/settlement and TLS; approve capacity, backup retention, RPO/RTO, restore drill and incident rollback. Authenticated finance-admin access, dual control and durable audit export remain unaccepted.

`config/cors.ts` contains a broad fallback list if origins are absent; Production acceptance must require explicit Production-only origin settings at startup rather than rely on that fallback. The currently accepted staging startup guard already enforces its single origin. The old `DEPLOYMENT.md` historical generic `.fugluck.com` cookie examples are superseded by the current host-only startup guard and current top-of-file staging settings.
