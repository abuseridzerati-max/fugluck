## Support and dispute procedure

1. Identify the user, operation/competition ID and environment without asking for card details, bank credentials, passwords or private keys. Preserve the report, timestamps and a correlation ID. Restrict support access to the minimum facts needed.
2. For a deposit or withdrawal complaint, read the immutable operation events, verified provider events and ledger transaction/postings; compare amount, currency, reference and timing. A success redirect or screenshot is evidence to investigate, never proof of settlement. If the provider state is unavailable, keep the operation pending/reviewed and escalate through the provider's approved channel.
3. For a competition result dispute, preserve immutable instance terms, participant/session binding, authority run version, server results, terminal decision, match record, settlement transaction and ledger reconciliation. Support/admin may investigate or void only through existing authorized lifecycle controls; they may not edit an authoritative score, winner or historical posting.
4. If a financial correction is warranted, use a new compensating ledger transaction linked to the original transaction, admin actor, reason and audit reference. A second reviewer/approval workflow and monetary limits require operator policy before launch. Never set a balance directly.
5. For suspected fraud or account takeover, record trusted server/provider signals, create a review case and apply explicit action-scoped restrictions. The local review store records immutable actions; the production review/appeal policy, retention and notification text require legal and operations approval.

## Reconciliation and incident triggers

The local reconciliation checks posting zero-sum, unbalanced/duplicate prize transactions, provider success without a ledger result, a ledger terminal status without an applied signed provider event, amount/currency mismatch, unmatched/out-of-order events, and pending operations older than one hour. That one-hour value is an engineering alert placeholder, not an accepted customer SLA. Production monitoring must set operator-approved thresholds and page owners for webhook failures, payout backlog, reconciliation discrepancies, migration/DB readiness, authority errors and settlement exceptions. No financial discrepancy should be silently auto-corrected.
